  The middleware is concise and correctly uses next-auth/jwt for token verification. The main risk is that the matcher only covers /login and /data-entry, leaving all other routes unprotected by middleware-level auth checks. This means unauthenticated users can access any other route (e.g., /dashboard/student) directly, relying solely on client-side or per-API checks.   [HIGH] authentication -- Line 53
  Middleware matcher only covers /login and /data-entry paths. All other routes (e.g., /dashboard/*, /api/*) are unprotected by middleware-level auth checks, allowing unauthenticated users to access them directly. This shifts the auth burden to individual pages/APIs and can lead to inconsistent enforcement.
  Fix: Expand the matcher to cover all protected routes, or add a catch-all check in the middleware that redirects unauthenticated users to /login for any protected path.

  Fix: Add a startup check that validates NEXTAUTH_SECRET is set, or wrap getToken in a try/catch with a fallback redirect to /login.

  [MEDIUM] authentication -- Line 36
